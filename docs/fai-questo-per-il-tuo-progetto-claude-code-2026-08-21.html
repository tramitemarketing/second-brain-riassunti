In sintesi: la guida per non tecnici al passo che viene dopo il vibe-coding — trasformare l'app che vive sul tuo computer in un servizio pubblico e sicuro: Supabase per database e autenticazione (con la row level security), Vercel o Netlify per l'hosting e per nascondere la chiave API, GitHub come perno, e — solo se il servizio è multi-step — una macchina in cloud scegliendo il giusto livello di astrazione (Railway prima di Hostinger, Hostinger prima di AWS).

La domanda e l'esempio guida

Chi crea un'applicazione in locale con Claude Code arriva sempre alla stessa domanda: e adesso come la faccio usare agli altri? Quali infrastrutture servono, come si pubblica in sicurezza, quali provider rendono tutto semplice e senza costi extra? Fontanel risponde con un esempio guida, "Finance AI": l'utente carica le proprie spese e l'app gli restituisce un piano di risparmio. Quello che hai già costruito è il frontend — l'interfaccia che diventerà il sito; tutto il resto è backend: la parte che serve davvero gli utenti.

Database e autenticazione: Supabase con la row level security

Il database si può pensare come un file Excel dove salvi i dati dei tuoi utenti (le spese caricate, i piani generati da rileggere in futuro), che il sito contatta via chiamate HTTP alle sue API. E dove c'è un database multi-utente c'è il problema di sicurezza numero uno: l'utente 1 non deve poter interrogare i dati degli utenti 2 e 3. Serve l'autenticazione: l'utente si identifica, e solo allora accede alla porzione di dati sua.

Il consiglio secco: Supabase, che racchiude database e autenticazione in un unico sistema. Salva qualsiasi tipo di dato (testo, numeri, immagini, file complessi — Fontanel lo chiama "database vettoriale": in realtà è Postgres relazionale, il vettoriale è un'estensione) e gestisce la sicurezza col meccanismo RLS, row level security: il punto da capire è che la sicurezza è impostata a livello di dato dentro il database — non serve alcuna logica esterna che scarichi tutto e filtri; quando l'utente fa la richiesta, dal db escono solo i dati di sua competenza. Supabase ha oltre 100.000 stelle su GitHub, documentazione completa, un'interfaccia comoda (tabelle a sinistra, pannello auth), e Claude Code lo conosce benissimo: puoi fargli fare il setup come vuoi tu.

Il servizio "a chiamata singola" e il problema della chiave API

Se il servizio è semplice, il giro è: sito → chiamata alle API di Anthropic → piano di risparmio → utente. Niente macchine, niente orchestrazione. Ma c'è un'accortezza obbligatoria: per chiamare Anthropic serve la tua chiave API, e se finisce nel frontend chiunque può rubarla — bastano gli strumenti di inspection del browser (si vedono i pacchetti di rete) o software dedicati — e bruciarti il credito.

Qui entrano i suoi due provider preferiti: Vercel e Netlify (li usa indistintamente; i piani gratuiti bastano per la maggior parte degli usi). Fanno due cose: l'hosting — il sito passa dal tuo computer a un URL raggiungibile da tutti — e la gestione delle chiavi API: la chiave viene nascosta dietro una serverless function, così chi usa il sito non può risalirci in alcun modo. Il flusso di lavoro è banale: il codice sta in una repository privata su GitHub («il social network del codice»: profili con codice pubblico o privato — le skill famose sono repo pubbliche di qualcuno), e su Vercel fai Add New Project → scegli la repo → deploy.

Quando serve una macchina in cloud

Non sempre basta una chiamata singola. Esempio esteso di Finance AI: dai dati dell'utente prima si fa una ricerca online sulla spesa media di una persona con quel profilo (geografia, età, stipendio, stile di vita), poi si rielabora tutto con le API di Anthropic in un piano step-by-step, poi si genera un PDF, poi lo si invia via email. Una catena di step interconnessi ha bisogno di un sistema che la racchiuda: input dall'utente → output finito (il PDF pronto). Quel sistema deve vivere su una macchina.

Perché non il tuo computer? Deve stare sempre acceso, contiene documenti che non c'entrano nulla, rallenta, e non scala. Una macchina fisica dedicata sotto la scrivania è accettabile, ma va configurata e mantenuta. La macchina in cloud ti dà l'esclusività senza i grattacapi: se il nodo cade, il provider la sposta e il servizio non si interrompe; monitoraggio e costi sono gestiti.

La scala di astrazione: Railway → Hostinger → GCP/AWS

La scelta del provider è una scala di astrazione, e conviene stare più in alto possibile:

  1. Railway — la prima scelta se vuoi occuparti solo del servizio: gli dai la repository GitHub e fa tutto lui (crea la macchina, gestisce i problemi).
  2. Hostinger — costi minori e libertà maggiore: in pochi click hai una VPS a cui ti colleghi, scarichi il codice da GitHub e avvii tu l'applicazione.
  3. Google Cloud / AWS — i provider "veri", ma per Fontanel non ha senso usarli direttamente: sono complicati, con una curva di apprendimento ripida. «Hostinger è nato per astrarre la complessità di questi provider, e Railway astrae ulteriormente Hostinger.»

Il messaggio finale: con questi mattoni — Supabase, Vercel/Netlify, GitHub, e all'occorrenza Railway o una VPS — spostare un'app dal Claude locale al pubblico è a portata di non tecnico, gratis o quasi.
